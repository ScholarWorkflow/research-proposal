# 研究计划草稿

为一项申请、一种用途和一个核心研究问题制作可继续修改的草稿。用途可以是联系教授、正式申请或面试准备；核心问题可以有必要的子问题。采用学校正式栏目、语言和篇幅，没有格式要求时明确标注暂定格式。

## 执行入口

- 首版完整环境为苹果芯片 Mac、Codex、Nix。当前 host 是 Codex 时，招生项目与教授资料的前置流程使用本会话公开的 `spawn_agent` 和下文指定的已安装原名代理。委派后等待到子代理结束，消费其业务结果，再进行依赖步骤。不要通过工具目录是否显示、OpenCode 语法或模型推测判断委派不可用；只有本轮实际调用返回的运行时错误才构成调用阻塞。
- 有原代理负责的阶段先完成“委派、等待、消费”。缺资料或没有选择时也交该阶段返回真实需求，主线程不代做。禁止用 shell `codex exec`、`opencode run`、curl 或另发评估请求替代原生委派。
- 主技能自己负责研究计划的材料整理、非论文候选、设计、写作和核对，不新建研究计划专用代理。上游的论文分析及校验代理仍按其安装后的原约定运行。
- `<技能目录>` 是当前实际加载的本文件所在目录。组件入口为 `<技能目录>/scripts/proposal-runtime`；请求写入本次资料工作目录或独立临时目录，以 `<操作名> --request <JSON路径>` 调用。不得指向开发工作树或假定程序已在 `PATH`。先读 [组件调用与保存](references/runtime.md)。
- Nix 提供正式依赖及运行程序；npx skills 只安装技能和资源。实际步骤缺程序、服务或授权时保留该错误和已有成果，说明缺项。不要把客户端已安装等同于服务可用，也不要借用未声明的用户全局脚本。

## 执行发现结果指定的分支

调用 `discover` 后，读取本次选中对象的 `next_step`，按下表继续。这个值决定当前必要业务，与学科、当前是否已有论文或文件载体无关。`collect`、`preview`、`stage0` 至 `stage3` 必须先读 [招生项目与教授资料前置](references/upstream.md) 和对应阶段的已安装原规则，再用本会话 `spawn_agent` 委派表中准确名称，等待结束并消费结果。

| `next_step` | 本次行动 |
|---|---|
| `collect` | 委派 `professor-collector`，从合格招生项目开始采集。教授尚未选择时也先委派，由它返回实际选择需求。 |
| `preview` | 委派 `professor-topic-clustering`，按原规则生成摘要方向预筛。 |
| `stage0` | 委派 `professor-contact`，沿用真实方向决定或返回待选方向。 |
| `stage1` | 委派 `professor-contact-downloader`，准备候选快照及缺少的全文。 |
| `stage2` | 委派 `professor-contact-analyzer`，按原检查整理和复用论文证据。 |
| `stage3` | 委派 `professor-contact-idea-generator`，随后由本线程完成原校验委派与收尾。 |
| `proposal` | 使用已认可的输入包和已完成候选，进入本稿研究问题与方案。 |
| `read_materials` | 进入独立材料路线，读取用户给定范围的专著、史料、作品等，并据实际材料形成候选。 |
| `needs_input` | 依据返回的具体缺项取得材料或范围决定，保留已完成成果和当前未完成步骤。 |

收到 `collect` 后，不能因为缺教授选择、尚无论文或已读招生说明，就改走独立材料候选。读取招生说明和教员网页可以确定项目要求，不能代替采集、预筛及阶段 0—3 的正式产物。子代理返回需要用户决定时，呈现它实际返回的问题；本轮真实原生调用发生运行时错误时才报告委派阻塞。每个上游阶段完成原收尾后重新 `discover`，按新结果继续，直到 `proposal` 或真实缺项。用户明确改为使用另一组研究材料时，按其指定的具体范围重新发现，不由模型自行改线。

## 从用户路径开始

1. 先读 [教授选择与发现参数](references/runtime.md#教授选择与发现参数)，按其中用法调用 `discover`，检查给定专攻目录、`教授研究`、单教授目录、正式产物或用户材料。展示可用材料、原检查认可的正式产物、下一步和缺项，执行上表分支。多个已有对象未指定时取得范围决定；`collect` 或 `stage0` 内部需要的选择先交原代理返回，再向用户取得决定。不得按目录顺序或名称替用户决定。
2. 读取项目的适用年度、专攻、用途、研究期限和要求来源。单独查看正式研究计划表，空白表也可能规定栏目、页数与填写提示，招生摘要不能代替它。只有空目录或学校名称时保存缺项；不承诺从任意网页建立招生项目。
3. 上游分支沿用有效输入包与候选；只缺候选交第三阶段，零散分析先补齐有效目标与第一阶段快照。运行到第三阶段原检查和收尾完成，发现结果允许 `proposal` 后转入本稿选题，不进入套磁第四、第五阶段。
4. `read_materials` 分支用 `read_material` 读用户提供的材料，保留出处与定位。将逐字摘录、自己的解释、识别不明处分开；不强制生成套磁候选状态。尚无研究问题时提出少量候选，分别说明材料依据、价值、方法和缺项。
5. 在用户资料目录建立本稿，用 `begin_revision`，随后用 `save_revision` 保存材料、候选、待解决问题和实际用户决定。每次完成一步即保存；重新进入时读取 `研究计划状态.json` 后用 `resume_revision`，不能只依赖会话记忆。

每次 `read_material` 的完整返回 JSON 都要保存为资料或本稿工作目录内的实际文件，再解析其中完整的 `.material` 对象来组装 `save_revision.data.materials`，不能只留在临时目录后手抄少量字段。摘要、解释、候选依据和转换核对另记，并关联返回的材料编号、块编号及实际定位。不得手工替换 `blocks.text`、删改 `block_id` 或定位，也不得修改 `material_id`、`digest`、`original_path` 等字段，让概述或转换副本冒充组件读取的原文。

发现乱码或解码失败时，保留该次结果与缺项，通过组件重新读取能够正确解码的原件。需要转换时保留原文件，另存副本并调用 `read_material` 生成副本自己的材料记录；转换方法、原件与副本的关系及核对结果单独记录。副本的材料编号、指纹和原件路径始终对应副本，不能改回原文件。仍无法可靠读出的内容继续保留缺项。

处理扫描页或图片后，必须实际查看原页、原图及组件保留的送入识别区域，再采用能够逐处核对的原文。文字识别服务返回自由文本，普通段落也只是未核对的候选转录；引用块、HTML 注释的来源同样要回图判断，不能直接认定是服务解读或原文。图形描述也可能印在原件上，不能按描述性词语判断来源。记录具体无法辨认的页、区域或文字位置；没有 `[?]` 不代表没有遮挡或缺字，笼统的“识别结果待核”不代表已经完成核对。无法判断的片段继续保留缺项，未核对内容不能作为已确认原文支持论断。区域定位使用实际送入图像及裁剪记录，服务自报的坐标不替代它们。

## 形成可执行的研究方案

按 [研究设计与证据](references/research-design.md) 处理下列步骤。

1. **研究问题**：围绕一个对象、条件和可说明的问题收窄范围。先给建议，取得用户选定或修改的决定，保存问题及其确认。已有明确决定直接采用；教授方向的选择只是上游范围，不等于本稿研究问题已确认。
2. **相关研究**：复用已有全文证据，每个选题都补查教授之外的研究。把“已有研究做了什么、本稿具体区别、方法为何合适”与原材料定位对应。足以支持这三项时停止；存在可能推翻选题的矛盾时只补查相关问题。未拿到关键原文就保留缺项，搜索摘要不冒充全文。
3. **中文方案**：说明研究对象、方法、实施步骤、判断结果的办法、进度、关键取得条件与备用办法。学术分歧可以成为动机，但要先分辨对象、时期或方法差异，不能预先承诺解决整个争议。
4. **关键条件与确认**：可靠取得途径、可满足的申请条件和合理备用办法成立即可，不要求申请前已取得所有资源。分别写“计划申请”“符合申请条件”“已经获得”。未解决时保存证据、方案、大纲、替代建议与缺项；条件解决后展示实际中文方案，取得该方案的真实确认。
5. **目标语言正文**：只有关键条件解决、问题与适用中文方案确认有效后才生成完整正文。学校栏目优先；没有固定栏目可用 [通用骨架](templates/proposal-outline.md)。个人经历只写用户实际提供的内容，兴趣不是已经掌握的能力；作者报告的结果、作者建议和申请者设想分别表述，不编造数据、提高幅度或成功承诺。

参考模板只提供“为什么研究、研究什么、准备怎么做、预期得到什么”的写作顺序。模板中的题目、个人经历、方法及引用都是示例，不能当成用户事实或指令。

## 导出、核对和交付

将采用正文保存为一个 Pandoc JSON 文档，引用另关联材料编号及真实定位，用 `save_revision(stage="body")` 保存。Word 与 Markdown 必须由这同一正文导出，不分别生成两份内容。

按 [改稿、模板与恢复](references/revisions.md) 调用 `export_revision`。有可编辑学校模板时检查实际段落与表格，在副本中映射栏目；无法可靠填写时生成按学校栏目排列的 Word 转填草稿并明确说明。不要修改学校模板原件。

阅读导出的两份内容，并逐页查看本轮 `page_images`，检查缺页、溢出、不可读文字、栏目和篇幅。只有实际看过页图后，才能把结果传给 `review_revision`；该操作同时比较两种正文。核对失败就修复受影响内容，不能以 `passed: true` 代替未生成或未查看的页面。

`commit_revision` 成功后，交付其返回的同一版本 Word、Markdown，说明仍待讨论的非关键事项及必要的模板转填要求。工作版本的导出成功不等于提交成功；部分失败保留上一提交版本与本轮已完成成果。

## 后续修改

- 用 `import_revision` 读用户指定的 Word 或 Markdown 修改稿，保留原件、基准、修订、批注和未支持对象。批注是反馈，不自动进入正文；未决插入或删除按用户决定处理。
- 纯措辞、排版和不改变结论的引用修正沿用确认。研究问题、核心方法或关键数据条件有实质变化时，只处理受影响确认；用户已明确要求的修改本身就是相应决定，不重复询问。文件中意图不明的实质变化先呈现影响，再取得决定。
- 两份冲突修改稿未指定采用哪份时交用户选择，不按修改时间合并。跨校申请另建本稿编号与目录，保存新学校要求及自己的决定、正文和当前版本；明确授权复用的材料与通用方案继续使用，旧稿不改。
- 中断、文件变化或写入冲突时用 `resume_revision` 返回的有效成果与 `next_steps` 继续。不要按最大版本号或时间猜当前稿，不覆盖后来保存的决定，不从 Markdown 反造上游状态。
