# 讲稿与想定问答

两份文件都由 `save_revision(stage="interview")` 保存结构化内容，再由
`export_revision` 生成 Markdown 交付文件。它们只在 `inputs.deliverables`
含 `script` 或 `qa` 时要求；没有加选的历史稿件不受影响。

- `script`：面试发表用的逐页讲稿，交付为 `研究计划讲稿.md`。
- `qa`：按类别整理的想定问答，交付为 `研究计划想定问答.md`。

两份文件都从研究计划正文派生，正文变了就要重新生成；正文没变时，改讲稿
只让讲稿自己失效，不需要重做正文和 Markdown。

## 讲稿内容

```json
{
  "script": {
    "timing": {
      "target_minutes": 10,
      "slides": 12,
      "chars_per_minute": 350,
      "tolerance_minutes": 1
    },
    "sections": [
      {
        "slide": 1,
        "title": "研究背景",
        "minutes": 1,
        "script": "这一页实际要说出口的完整句子。",
        "visual": "本页图的要点，可以不填"
      }
    ]
  }
}
```

检查规则：

- `sections` 的页数必须等于 `timing.slides`，页码从 1 连续编号且不重复。
- 每页要有 `title`、正数 `minutes` 和非空 `script`。
- 各页 `minutes` 合计与 `target_minutes` 的差不能超过 `tolerance_minutes`。
- 讲稿总字数除以 `chars_per_minute` 与目标时长的差也不能超过同一误差。
  字数按非空白字符统计。日语口述一般每分钟 300 至 400 字，中文 200 至 260 字；
  `chars_per_minute` 必须落在 100 至 700 之间。
- `visual` 是可选的字符串，写这一页图里放什么，不写就说这页靠什么画面支撑。

各页时间怎么分，取学校要求里写明的发表时间。要项只写总时长时，按每页
一分钟左右估算页数，再把时间按论点重要程度分配；时间对不上就先改内容，
不要只改 `minutes` 数字让检查通过。

## 想定问答内容

```json
{
  "qa": {
    "chars_per_minute": 350,
    "max_answer_minutes": 1.5,
    "required_categories": ["研究计划相关", "方法与新规性", "可行性与期限", "研究不足"],
    "items": [
      {
        "category": "方法与新规性",
        "question": "为什么用这个方法？",
        "answer": "一到两句能当场说出口的答案。",
        "source": "正文第几段或材料编号与定位"
      }
    ]
  }
}
```

检查规则：

- `items` 不能为空；每个类别的 `category` 必须出现在 `required_categories` 里。
- `required_categories` 里每个类别至少要有一条问题，不能整类漏掉。
- 每条答案按 `chars_per_minute` 折算的时长不能超过 `max_answer_minutes`；省略该项时
  按 1.5 分钟检查，建议按学校要项或自己的语速明确写出。
- `source` 可选，写这条答案依据的正文段落或材料定位。

类别不是固定清单。依据目标学校要项、作品形式和个人经历，在
`required_categories` 里写出这场面试真正会问的几类；不确定时至少覆盖研究
计划本身、方法与新颖性、可行性与期限、研究不足四项。答案要写成能开口说
的句子，不要写成小作文。

## 调用顺序

1. 正文步骤保存并确认后，用 `save_revision(stage="interview")` 保存这两项内容。
   一次调用可以只交 `script` 或只交 `qa`；加选却未交的那项会返回
   `interview_missing`，已交的部分照样保存。后一次保存会把步骤里已有的另一项
   带上，因此补齐缺项不必重写全部内容；本次请求里显式给出的那一项覆盖旧值。
2. 内容检查不通过时返回 `needs_input`，逐条给出问题，同时把已写好的内容
   落盘。按返回的问题补齐后再次保存，不必重写全部内容。
3. 讲稿步骤只能覆盖、不能删除单项。要把某项撤掉，请建立新的工作版本后只保存
   要保留的内容；把该项写成空值不会清除已保存的内容。
4. 保存过的内容一律参与检查，即使那一项没有在本稿 `deliverables` 里加选。未加选
   的内容有问题时，讲稿步骤会保持未完成，并阻塞已加选文件的导出；需要清空时按上
   一条处理。
5. `export_revision` 省略 `formats` 时生成本稿全部已选加的文件；只重新生成
   讲稿时传 `formats:["script"]`。没有在 `deliverables` 里加选的文件不能导出。
6. `review_revision` 读回两份 Markdown，与已保存内容重新生成的文本比较。
   交付文件被手改、内容与保存件不符时核对失败，需要重新保存内容或重新导出，
   不能直接改 Markdown 后提交。

## 与其他交付文件的关系

- 讲稿依据正文和已确认的研究问题、中文方案。正文或方案变了，讲稿与想定问答
  一起失效，不能只改讲稿里引用的数字。
- 生成讲稿不改变正文、Markdown 或它们的核对结论；没有加选讲稿的稿件完全
  不经过这一步。
- 提交时，加选的讲稿和想定问答与 Markdown 一起进入同一版本目录。提交成功后
  返回的 `artifacts` 会列出实际文件路径。
